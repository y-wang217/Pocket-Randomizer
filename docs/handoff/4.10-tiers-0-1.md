## How this project is being run, and why

**The design bible outranks the milestone list on every presentation question.**
That is `CLAUDE.md`'s rule and the lead designer restated it: *"The Bible wins in
every case. Highlight for me exact discrepancies so I can resolve each case by
case."*

So nothing is built around a conflict. Every place the list and the bible
disagree becomes a row in
[`../design/bible-discrepancies.md`](../design/bible-discrepancies.md) with the
section, the line, the options and a recommendation — and the item waits. **Keep
doing this.** Fifteen rows so far; thirteen ruled, two open.

The bible is at **Rev 2**, carrying seven amendments, each marked inline with the
row that produced it. No rule changed: six corrected a table, an ordering or a
glossary entry that disagreed with a rule, and the seventh defined a term R6 was
already using.

### Branch shape

The list says one item, one PR. The lead designer asked for one 4.10 branch
instead, and D13 reconciles them: **one sub-branch per item, `visual/4.10-<item>`,
merged back into the trunk with `--no-ff` and no squash**, so every item reverts
alone at its merge commit. Keep that shape.

### The gate

`npm test` is the gate and it takes **~11 minutes**. Run it in the background and
wait. Two things to know:

1. **`exit=1` with zero failures is normal here.** Vitest's reporter RPC times out
   under load; `scripts/check.mjs` already classifies exactly this as `ERRORED`
   rather than `FAILED` (`everyTestPassedAnyway`). Check `grep -c "FAIL "` before
   believing an exit code.
2. **The browser suite is load-sensitive.** See the open item below.

## One item that does not exist yet and probably should

**The browser suite is load-sensitive and it will produce false reds overnight.**

`test/visual-move-cards.test.ts` and `test/visual-v0.test.ts` each failed once
under full-suite load during these six items, and each passes in isolation in
seconds. The cause is structural, not flaky hardware:

> `playUntil` and `stepOnce` in `scripts/visual/browser.mjs` walk the app with
> fixed `await page.waitForTimeout(25)` between steps and a step budget. The waits
> are wall-clock rather than state, so on a saturated machine a step that has not
> finished rendering is counted as a step taken, and the walk exhausts its budget
> before reaching the last surface.

That is the same class of wall-clock assertion
[`../visual/reports/patch-battle-animation.md`](../visual/reports/patch-battle-animation.md)
retired elsewhere in this tree. It is nobody's item so far because it belongs to
none of them. **Before any unattended overnight run, make it one.**

## Conventions worth keeping

- **`contentHash` discipline.** D12 ruled: per-file split, never a hash move.
  `src/data/displayTuning.ts` is the precedent; the exclusion rule is mechanical
  and `test/content-hash.test.ts` walks the import graph to hold it. Four new
  excluded files landed this way (`forbiddenWords`, `glyphFamilies`, plus the
  additions to `displayTuning`).
- **Deviations go in `docs/generation.md`, never into the prompt.** Section 52 is
  this release's first: the census measures sixteen surfaces where M0.1 asked for
  fourteen, and says why.
- **Generated files are generated.** `docs/copy.md` (`npm run copy-audit`) and
  `docs/design/text-census.md` (`npm run census`) are rebuilt, never edited. Rebuild
  both after any copy change.
- **A test whose premise the design changed gets updated, not weakened.** M1.2
  rewrote `battle-readout.test.ts`'s "opens in one tap" to a long press and kept
  every assertion about what the panel contains.
